# Session ID as Path Parameter

**Status:** Open · **Type:** Design · **Author:** franky · **Date:** 2025

## 1. Problem

The franky proxy HTTP API has two parallel addressing schemes for sessions:

| Current endpoint | Addresses | Style |
|---|---|---|
| `GET /transcript` | active session only | implicit |
| `GET /session` | active session info | implicit |
| `GET /sessions/{id}/transcript` | any session by id | explicit path param |
| `GET /sessions` | all sessions | list |
| `POST /session/new` | creates + activates | mutation |
| `POST /session/activate` | switch active | mutation |
| `GET /events` | active session only | implicit |
| `POST /prompt` | active session only | implicit |

There is **one active session** per process and the agent loop is not
reentrant (`run_mutex`). Yet the web UI sidebar already lists all
sessions and lets the user browse older transcripts. The
`/sessions/{id}/transcript` endpoint exists for read-only browsing.

**Problem:** The _read-only_ browsing endpoints (`/transcript`,
`/session`) only work for the active session. A user who opens a
bookmark to `http://franky.local/` returns to the _current_ active
session, not the session they were looking at. There is no way to
link directly to a specific session.

**Goal:** Make the session identity a first-class part of the URL so:

1. A link (bookmark, chat notification) can deep-link into a specific
   session for read-only viewing.
2. The same URL path scheme works for both the active session and
   historical sessions — `/sessions/<id>/transcript` already exists,
   but `/events/<id>` and `/prompt/<id>` do not.
3. The concept of "active session" still exists (the loop can only
   run one turn at a time, so /prompt and /events SSE always attach
   to whichever session is active).

## 2. Design

### 2.1 Principle: only the active session accepts mutation

The following operations always target the **active session** and
require no session id in the path:

| Method | Path | Reason |
|--------|------|--------|
| `POST` | `/prompt` | Agent loop is single-threaded |
| `GET` | `/events` | SSE stream follows the active session |
| `POST` | `/abort` | Cancel the in-flight turn |
| `POST` | `/interrupt` | Graceful stop |
| `POST` | `/command` | Slash commands mutate active session state |

**All read-only operations** accept an optional session id as a path
parameter. When omitted they default to the active session (backward
compatible). When present they return data for any persisted session:

### 2.2 New path scheme

```
GET    /sessions/{sessionId}/transcript   (already exists)
GET    /sessions/{sessionId}              (new — session info/metadata)
GET    /sessions/{sessionId}/events       (new — replay events for a historical session — stretch goal)

# Active-session aliases (backward compat, still work)
GET    /transcript                        → /sessions/{active}/transcript
GET    /session                           → /sessions/{active}
GET    /events                            → /sessions/{active}/events
```

### 2.3 Server-side routing

The `handleConnection` function gains a helper `resolveSessionId`:

```zig
/// Return the session id from the path if present and valid,
/// otherwise fall back to the active session's id. Returns null
/// on parse failure (malformed id, path too short).
fn resolveSessionId(path: []const u8, active_id: []const u8) ?[]const u8 {
    // Paths: /sessions/<id>/transcript, /sessions/<id>, /sessions/<id>/events
    const prefix = "/sessions/";
    if (!std.mem.startsWith(u8, path, prefix)) return active_id;
    const tail = path[prefix.len..];
    const slash = std.mem.indexOfScalar(u8, tail, '/');
    const id = if (slash) |pos| tail[0..pos] else tail;
    if (!isUlidLike(id)) return null;
    return id;
}
```

Routes are then matched in this order:

1. **Static resource routes** (`/health`, `/app.js`, `/style.css`,
   `/`, `/design-docs`, `/design-docs/archive`) — no session context.
2. **Mutation routes** (`/prompt`, `/abort`, `/interrupt`,
   `/restart`, `/permission/resolve`, `/command`, `/session/new`,
   `/session/activate`) — always active session.
3. **Read routes with optional session id** — check path prefix:
   - `GET /transcript` → redirect / alias to
     `GET /sessions/{activeId}/transcript`
   - `GET /session` → `GET /sessions/{activeId}`
   - `GET /sessions/{id}/transcript` → already exists
   - `GET /sessions/{id}` → new, returns session header + metadata
   - `GET /events` → SSE for active session (unchanged)
4. **Static asset fallthrough** same as today (`.html`, `.js`, `.css`).

### 2.4 New endpoint: `GET /sessions/{id}`

Returns the session header (id, title, timestamps, model, provider)
without loading the full transcript. This is analogous to the
`session.json` header file on disk. Response shape:

```json
{
  "id": "01JXTEST...",
  "title": "Fix authentication bug",
  "createdAtMs": 1712000000000,
  "updatedAtMs": 1712000500000,
  "messageCount": 12,
  "provider": "openai-gateway",
  "model": "deepseek-chat",
  "api": "openai-gateway",
  "active": false
}
```

The `active` boolean is `true` when the requested id matches the
active session's id.

### 2.5 Web UI routing

The web UI (`app.js`) already has `activeSessionId` and
`sessionsCache` globals. The changes are:

1. **On page load:** Parse `window.location.hash` for a session id
   fragment (e.g. `#/sessions/01JXTEST...`). If present and valid,
   set `activeSessionId` from the hash and fetch
   `GET /sessions/{id}/transcript` + `GET /sessions/{id}` for the
   initial render instead of `GET /transcript`. The SSE stream
   (`/events`) still connects to the _server's_ active session — the
   UI shows a banner "Viewing historical session — prompts will go to
   the active session" when the hash id differs from the server's
   active id.

2. **Session sidebar:** Clicking a session in the sidebar either:
   - Switches active session (server-side `POST /session/activate`),
     or
   - Opens it for read-only viewing (client-side hash update,
     fetches transcript without switching server active).

   Default behavior remains "switch active" (current UX). Holding
   modifier key (Ctrl/Cmd+click) opens read-only.

3. **Browser URL updates:** When the active session changes (via
   `session_switched` SSE or `POST /session/activate` response),
   `window.location.hash` updates to `#/sessions/{newId}` so a
   browser refresh returns to the same session.

4. **Deep-link flow:**
   ```
   1. User opens http://franky.local/#/sessions/01JABCD...
   2. UI reads hash, fetches GET /sessions/{id} for metadata
   3. UI fetches GET /sessions/{id}/transcript for messages
   4. UI connects GET /events for live updates
   5. Banner shows: "Viewing session 01JABCD... •
      Active session: 01JXYZW... (click to switch)"
   ```

### 2.6 SSE considerations

`GET /events` always streams the **active session**'s events. When
the server switches active session (via `POST /session/activate` or
`POST /session/new`), the existing `session_switched` SSE event
already tells the client to rehydrate. The client's UI then shows the
correct session.

If we want historical-event replay for a non-active session
(**stretch goal**), we could add `GET /sessions/{id}/events`. This
would replay the recorded event JSONL from disk (if `--record-events`
was on) or the replay ring for the current process. This is low
priority — the transcript JSON is sufficient for read-only browsing.

### 2.7 Summary of route changes

| Method | Old path | New path | Notes |
|--------|----------|----------|-------|
| `GET` | `/transcript` | kept + `/sessions/{id}/transcript` | Backward compat, new path already exists |
| `GET` | `/session` | kept + `/sessions/{id}` | Backward compat, `/sessions/{id}` is new |
| `GET` | `/events` | kept (always active) | No change |
| `GET` | `/sessions` | kept | No change |
| `GET` | `/sessions/{id}/transcript` | kept | Already exists |
| `POST` | `/session/new` | kept | Always creates + activates |
| `POST` | `/session/activate` | kept | Always switches server active |
| `GET` | — | `/sessions/{id}` | **New** — session metadata |

## 3. Migration

**No breaking changes.** Every existing URL keeps working. The new
`/sessions/{id}` endpoint and URL hash deep-linking are additive.

**Phase 1** (this PR):
- Implement `GET /sessions/{id}` server-side handler
- Add `resolveSessionId` helper to `handleConnection`
- Update `GET /transcript` to internally delegate to
  `/sessions/{activeId}/transcript` (no behavior change)
- Add URL hash routing in `app.js`
- Add read-only sidebar click support (Ctrl/Cmd+click)

**Phase 2** (future):
- `GET /sessions/{id}/events` for historical SSE replay
- Orchestrator API spec update for `/sessions/{id}`

## 4. Open Questions

1. **Should `POST /prompt/<id>` exist?** No — it would race with the
   active session's `run_mutex`. If you want to prompt a different
   session, `POST /session/activate` first, then `POST /prompt`. The
   two-step is explicit about the active-session switch.

2. **Should the SSE stream switch automatically when URL hash
   changes?** No — the server has one active session and one SSE
   stream. The client can display a "viewing historical" banner but
   the SSE firehose always reflects the server's active session. This
   is a deliberate simplification.

3. **Should `GET /sessions/{id}` load the full transcript?** No —
   just the header/metadata. Transcripts can be large (megabytes of
   tool output). The client fetches transcript separately via
   `GET /sessions/{id}/transcript` only when the user clicks into a
   session. The sidebar list already avoids loading transcripts for
   every entry.
