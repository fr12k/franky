# Session ID as Path Parameter

**Status:** open for design discussion  
**Decision date:** TBD  
**Scope:** web UI (proxy mode) — backend routing + frontend navigation  
**Affected files:**
- `src/coding/modes/proxy.zig` — HTTP routing, session activation
- `src/coding/modes/web/app.js` — client-side routing, session management
- `src/coding/modes/web/index.html` — structural updates (if required)
- `src/coding/modes/web/style.css` — optional styling for session navigation

---

## Current State

The proxy mode web UI is **single-session** — one process, one active transcript.
Session switching is done via POST requests:

| Endpoint | Method | Purpose |
|---|---|---|
| `POST /session/new` | POST | Mint a fresh ULID, switch to it |
| `POST /session/activate` | POST | Switch to a persisted session (body: `{"id":"<ulid>"}`) |
| `GET /sessions` | GET | Enumerate persisted sessions |
| `GET /sessions/<id>/transcript` | GET | Load a persisted session's transcript (read-only) |

The active session is identified by `session.session_id` (a ULID stored in the
`Session` struct). The web UI sidebar lists all persisted sessions and clicking
one fires `POST /session/activate` which mutates the server-side session state
in-place, then broadcasts a `session_switched` SSE event to all subscribers.

**Key limitation:** The URL bar always shows `http://127.0.0.1:8787/` regardless
of which session is active. There is no way to:
- Bookmark a specific session
- Share a link to a session
- Open multiple sessions in different browser tabs (they all share the same
  server-side active session)
- Use the browser's back/forward buttons to navigate session history

---

## Design Goals

1. **URL-addressable sessions** — each session has a unique URL path
   (`/session/<ulid>`) that can be bookmarked, shared, and opened in a new tab.
2. **Multiple tabs** — different browser tabs can view different sessions
   simultaneously without interfering with each other.
3. **Back/forward navigation** — browser history works naturally when switching
   sessions.
4. **Backward compatibility** — existing `/session/new`, `/session/activate`,
   and `/sessions` API endpoints continue to work. The root `/` redirects to
   the active session's path.
5. **Single active session** — the server still has one "active" session that
   accepts `/prompt` and `/events` connections. Other sessions are view-only
   (read transcript, see messages) but cannot be prompted into.

## Proposed Design

### URL Scheme

```
/                          → redirect to /session/<active_ulid>
/session/<ulid>            → web UI for a specific session (active or view-only)
/session/<ulid>/events     → SSE stream for this session (only if it's the active one)
/session/<ulid>/prompt     → POST prompt (only if it's the active one)
/session/<ulid>/transcript → GET transcript for this session
```

### Backend Changes (proxy.zig)

#### 1. Route registration

Add a new route handler that matches `GET /session/<ulid>` (and optionally
`GET /session/<ulid>/index.html`). This serves the same web UI HTML page
but with a `<meta>` tag or inline script that tells the frontend which
session to load.

The existing flat routes remain:

```
GET /sessions              → respondSessionList (unchanged)
POST /session/new          → respondNewSession (unchanged)
POST /session/activate     → respondActivateSession (unchanged)
GET /sessions/<id>/transcript → respondSessionTranscript (unchanged)
```

New routes:

```
GET /session/<ulid>        → respondSessionPage
GET /session/<ulid>/transcript → respondSessionTranscriptById (or reuse existing)
```

#### 2. Session-scoped event streams

Currently there is one `/events` endpoint that streams events for the active
session. With path-parameter sessions, we need to decide:

**Option A (recommended):** Only the active session gets live SSE events.
View-only sessions return a static transcript. The `/events` endpoint moves
to `/session/<ulid>/events` and returns a 404 (or 409 Conflict) if the
requested session is not the active one.

**Option B:** Multiple sessions can have active SSE streams. This would
require significant rework of the subscriber model (currently a fixed-size
array on the `Session` struct). Not recommended for v1.

#### 3. Active session indicator in responses

The `GET /sessions` response already includes an `"active"` field with the
active session's ULID. This is sufficient for the frontend to know which
session is the "live" one.

### Frontend Changes (app.js)

#### 1. Client-side routing

On page load, the frontend reads the session ID from the URL path:

```javascript
// Extract session ID from URL path
// /session/<ulid> → ulid
// /              → fetch /session to get active ID
function getSessionIdFromUrl() {
    const match = window.location.pathname.match(/^\/session\/([a-zA-Z0-9_]+)/);
    return match ? match[1] : null;
}
```

#### 2. Session switching via URL

When the user clicks a session in the sidebar:

1. If the clicked session is the active one → navigate to `/session/<id>`
   (pushState, no server round-trip for the transcript — already cached).
2. If the clicked session is NOT the active one → show a "view-only" badge
   and load the transcript via `GET /session/<id>/transcript`. The prompt
   input is disabled. A banner offers "Switch to this session" which calls
   `POST /session/activate` and then navigates to the new active session URL.

#### 3. History API

Use `history.pushState` / `popstate` for session navigation so the browser
back/forward buttons work:

```javascript
function navigateToSession(id) {
    const url = `/session/${id}`;
    history.pushState({ sessionId: id }, '', url);
    loadSessionView(id);
}

window.addEventListener('popstate', (e) => {
    const id = getSessionIdFromUrl();
    if (id) loadSessionView(id);
});
```

#### 4. Active session banner

When viewing a non-active session, show a banner at the top:

> 🔵 Viewing session `<title>` — this session is read-only.
> [Switch to this session] [Back to active session]

When viewing the active session, show the normal prompt input.

### View-Only Session Behavior

| Feature | Active Session | View-Only Session |
|---|---|---|
| Prompt input | Enabled | Disabled, with banner |
| SSE events | Live stream | Not available |
| Transcript | Live + persisted | Persisted only |
| Tool results | Expandable | Expandable |
| Session switch | N/A | Banner with switch button |
| URL | `/session/<active_id>` | `/session/<other_id>` |

## Open Questions

1. **Should view-only sessions get SSE streams?** Option A says no (simpler).
   Option B would allow watching a session progress from a different tab, but
   adds complexity. Recommend starting with Option A.

2. **How does the active session change affect other tabs?** When tab A
   switches the active session via `POST /session/activate`, tab B (on the
   old active session) should detect this. The `session_switched` SSE event
   already broadcasts to all subscribers. Tab B can listen for it and show
   a banner: "The active session has changed. [Reload]" or auto-navigate.

3. **Should `/session/<ulid>` work for non-persisted sessions?** If
   `--no-session` is set, there is no disk persistence. The active session
   still exists in memory. We could still serve it at `/session/<ulid>` as
   long as it's the active session. Non-active, non-persisted sessions
   cannot be viewed (404).

4. **What about the `/events` endpoint?** Keep `GET /events` as a shorthand
   for `GET /session/<active_id>/events` for backward compatibility. The
   canonical path is the session-scoped one.

---

## Migration Path

1. **Phase 1 — URL reading + navigation (backward-compatible)**
   - Add `GET /session/<ulid>` route that serves the web UI HTML with a
     session ID hint.
   - Frontend reads session ID from URL and loads the appropriate transcript.
   - Root `/` redirects to `/session/<active_id>`.
   - All existing API endpoints remain unchanged.

2. **Phase 2 — View-only sessions**
   - Add view-only mode for non-active sessions.
   - Disable prompt input, show banner.
   - Add "Switch to this session" flow.

3. **Phase 3 — Multi-tab coordination (optional)**
   - Handle `session_switched` events in non-active tabs.
   - Show notification when active session changes.

## Alternatives Considered

### Hash-based routing (`/#/session/<ulid>`)

Simpler to implement (no server-side changes needed for routing), but:
- URLs are not shareable (hash is not sent to the server)
- Server-side rendering / SEO is impossible
- Breaks if the user opens the URL in a new tab (no server knows the session)

**Decision:** Path parameters are preferred for shareability.

### Query parameter (`/?session=<ulid>`)

Even simpler, but:
- Less RESTful
- Doesn't compose well with future path-based features
- Can conflict with other query parameters

**Decision:** Path parameter is the standard REST approach.

### Full multi-session server (multiple active sessions)

The server would maintain N active sessions, each with its own event stream
and prompt queue. This is a major architectural change — the current design
is explicitly single-session (see proxy.zig line 38-41). Not recommended
for this iteration.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| **URL manipulation** — user edits the ULID in the URL bar | Validate ULID format server-side; return 404 for invalid/missing sessions |
| **Memory pressure** — many view-only sessions loaded | Each view-only load is a disk read; no persistent memory allocation beyond the response |
| **SSE connection per tab** — each tab opens its own `/events` connection | Already the case today; the subscriber array caps at `max_subs` |
| **Backward compatibility** — existing bookmarks to `/` break | Root `/` redirects to `/session/<active_id>`; no breakage |
