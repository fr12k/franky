# v3.x — Auto mode (classifier-based permission gating)

> **Status:** Implemented (Phases 1–4 + interaction tests). Phase 5 (`/permissions` display helper, spec entry) partial.
> **Last updated:** 2025-11
> **Reference:** Claude Code "Configure auto mode" — https://code.claude.com/docs/en/auto-mode-config

## Problem

Franky currently has two permission layers:

1. **Role gate** (`security/role.zig`) — decides which *tools* the model
   sees at all (`read` / `plan` / `code` / `full`).
2. **Permission overlay** (`security/permissions.zig`) — a per-call
   gate (`Store.check`) returning `auto_allow` / `auto_deny` / `ask`,
   seeded from `settings.json` and `--allow-tools` / `--deny-tools` /
   `--ask-tools`, with a pause-and-prompt protocol for the `ask`
   branch.

The overlay is **static**: it matches on tool name and a coarse
verb-level bash fingerprint (`fingerprintBash` → first token, basename
stripped). It has no notion of *intent*, *destination*, or
*irreversibility*. So in practice users either:

- run with `--prompts` and get prompted on every `write` / `edit` /
  `bash` (tedious), or
- run with `--yes` and auto-allow *everything* (unsafe for unattended
  runs), or
- don't enable the gate at all (the default — no belt, no braces).

Claude Code's **auto mode** solves this with a third layer: a
*classifier* that runs *after* the static allow/deny/ask rules and
*before* execution. The classifier blocks anything irreversible,
destructive, or aimed outside the user's trusted environment, and
auto-approves everything else — so the model can run long tasks
without routine prompts while still being fenced against the genuinely
dangerous stuff.

This doc proposes adding an equivalent auto-mode layer to Franky.

## Goal

A `--auto` flag (and `autoMode` settings block) that:

- Auto-approves routine, reversible, in-scope tool calls.
- Blocks irreversible / destructive / exfiltration-y tool calls with
  an actionable denial message (names the matched rule).
- Honors existing `permissions.deny` / `permissions.ask` rules first
  (they are evaluated *before* the classifier, exactly like Claude
  Code).
- Is configurable via `settings.json` so an organization can declare
  its trusted repos / domains / buckets once.

## Non-goals (for this pass)

- A hosted / server-side classifier. Claude Code's classifier is an
  LLM-backed service. Franky is provider-agnostic and offline-capable,
  so v1 of auto mode will use a **local rule engine**, not an LLM call.
  An optional LLM-backed classifier is a natural follow-up but
  intentionally out of scope here — it adds latency, cost, and a
  hard dependency on a provider being reachable.
- Organization-managed settings distribution (Claude Code's "managed
  settings"). Franky has no org/tenant concept yet.
- The `/auto-mode-setup` slash command (Claude Code drafts environment
  entries from recent denials). Nice to have; deferred.

## Design

### Layering

```
tool_call arrives
   │
   ▼
┌─────────────────────────────────────┐
│ 1. Role gate (existing)             │  unknown/disabled tool → role_denied
└─────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────┐
│ 2. Static permission overlay        │  deny → auto_deny (hard block)
│    (existing Store.check)           │  ask → prompt (human checkpoint)
│    deny + ask evaluated FIRST       │  allow → fall through to step 3
└─────────────────────────────────────┘
   │  (decision == allow OR default-allow AND not auto mode → run)
   ▼
┌─────────────────────────────────────┐
│ 3. Auto-mode classifier (NEW)       │  block → auto_deny + rule name
│    only when --auto / autoMode on   │  pass  → auto_allow
└─────────────────────────────────────┘
   │
   ▼
   execute tool
```

Key invariants, matching Claude Code:

- **`deny` and `ask` rules win over the classifier.** A `permissions.deny`
  entry blocks before the classifier is consulted; an `ask` entry
  prompts regardless of what the classifier would say. This is already
  the case in `Store.check` (steps 1–3) — auto mode slots in as the
  *default policy* replacement.
- **`allow` rules are exceptions to classifier blocks.** A user-added
  `allow` entry lets a specific command through even if the classifier
  would block it. (Claude Code calls this additive: "a developer-added
  `allow` entry can override an organization `soft_deny`".)
- **The classifier never sees project-scoped `autoMode` config.**
  Claude Code deliberately ignores `autoMode` in
  `.claude/settings.json` because a checked-in repo could inject its
  own allow rules. Franky will mirror this: `autoMode` is read only
  from the **user** settings layer (`$FRANKY_HOME/settings.json`) and
  CLI `--settings`, never from the project layer.

### The classifier (v1: local rule engine)

A pure function over a normalized view of the tool call:

```zig
pub const ClassifierInput = struct {
    tool: []const u8,          // "bash", "write", "web_fetch", ...
    args_json: []const u8,     // raw args, for extraction
    workspace_root: []const u8,
    git_remotes: []const []const u8,   // trusted by default
    env: *const AutoEnv,               // user-declared trust boundary
};

pub const ClassifierVerdict = enum {
    pass,            // auto-approve
    block,           // auto-deny — reversible but out of scope
    block_hard,      // auto-deny — irreversible/destructive
};

pub const ClassifierResult = struct {
    verdict: ClassifierVerdict,
    rule_name: []const u8,   // e.g. "[Data Exfiltration]", "[Destructive Write]"
    reason: []const u8,      // human-readable, actionable
};
```

Rule families (mirroring Claude Code's default block rules):

| Family | What it catches | Example |
|--------|----------------|---------|
| **Destructive / irreversible** | `rm -rf`, `git push --force`, `git reset --hard` on tracked files, DB drops, `dd`, `mkfs` | `bash:rm -rf /` → block_hard `[Destructive Command]` |
| **Data exfiltration** | writes/POSTs/fetches to a destination *outside* the trusted environment | `web_fetch https://pastebin.com/...` → block `[Data Exfiltration]` |
| **Secrets egress** | commands that would send a secret-bearing env var or file to an external host | `curl $AWS_SECRET_ACCESS_KEY ...` → block `[Secrets Egress]` |
| **External write** | `write`/`edit` to a path outside `workspace_root` (already caught by `path_safety`, but the classifier makes it an *auto-deny with a named rule* rather than a generic error) | `write /etc/passwd` → block_hard `[External Write]` |
| **Untrusted SCM target** | `git push` to a remote not in `git_remotes` ∪ `env.trusted_repos` | `git push other-origin` → block `[Untrusted SCM Target]` |
| **MCP tool allow-list** | MCP tools (`mcp__<server>__<tool>`) not matching a safe read-family verb | `mcp__atlassian__delete_ticket` → block `[MCP Tool Not Allowed]` |

Each rule is a small function `fn(input) ?ClassifierResult` returning
null when it doesn't apply. The engine runs them in order; first match
wins, with `block_hard` rules checked before `block` rules so the
denial message reflects the more serious concern.

#### MCP tool allow-list

MCP tools are gated by an **allow-list** of safe read-family verbs
rather than a deny-list of destructive prefixes. This is the safer
default: novel MCP tools with unknown names (e.g. `deleteTicket`,
`purgeCache`) are blocked by default rather than silently
auto-approved. The safe verbs are:

`get`, `find`, `search`, `list`, `read`, `query`, `fetch`, `view`,
`show`, `describe`, `info`, `status`, `health`, `check`, `validate`,
`test`, `ping`, `whoami`, `count`, `stats`

An MCP tool passes when its remote tool name (the part after
`mcp__<server>__`) starts with one of these verbs at a word boundary
(followed by `_`, `-`, end-of-string, or a non-alphanumeric char).
Everything else soft-blocks with `[MCP Tool Not Allowed]` — the user
can add an `autoMode.allow` entry (e.g. `mcp__atlassian__*` or
`mcp__atlassian__create_issue`) to override.

### The `autoMode` settings block

New top-level key in `settings.json`, read **only from the user layer**
(`$FRANKY_HOME/settings.json`) and `--settings` inline JSON:

```jsonc
{
  "autoMode": {
    "environment": {
      "organization": "Acme",
      "primaryUse": "software_development",   // context slot
      "cloudProviders": ["gcp"],
      "repositoryVisibility": "private",
      "trustedRepos": ["github.com/acme/*"],
      "sourceControl": ["github.com"],
      "trustedDomains": ["*.internal.acme.com", "registry.acme.com"],
      "trustedBuckets": ["gs://acme-build-artifacts"],
      "keyInternalServices": ["https://ci.acme.com"],
      "internalPackageRegistries": ["npm.acme.com"],
      "cicdDeployTargets": ["gcp:projects/acme-prod"],
      "networkPosture": {
        "hostContainment": "container_with_egress_allowlist",
        "allowedHosts": ["*.acme.com", "github.com"],
        "cloudMetadataReachable": false
      }
    },
    "allow": ["Bash(go test *)", "Bash(zig build)"],     // exceptions to soft blocks
    "softDeny": [],                                       // org-level soft blocks
    "hardDeny": ["Bash(rm -rf *)"]                        // never, even with allow
  }
}
```

- `environment` → parsed into an `AutoEnv` struct the classifier
  receives on every call. Unset slots fall back to conservative
  defaults (same as Claude Code: private repo, open internet, no
  trusted buckets).
- `allow` → entries that override a `softDeny` / classifier `block`.
  They do **not** override `hardDeny` or `permissions.deny`.
- `softDeny` → organization soft blocks (classifier blocks, but an
  `allow` exception beats them).
- `hardDeny` → never-runs list; beats everything except
  `permissions.deny` (which is also a hard block, just expressed in
  the existing layer).

`hardDeny` ∪ `permissions.deny` is the set of "absolutely never"; the
distinction is mostly about *where* you express it. Keeping
`permissions.deny` as the primary hard-block mechanism preserves
back-compat; `hardDeny` is a convenience for grouping auto-mode-specific
nevers.

### Precedence (full order)

1. `permissions.deny` (hard block, before classifier) — existing.
2. `hardDeny` (hard block, before classifier) — new.
3. `permissions.ask` (prompt, before classifier) — existing.
4. `permissions.allow` / `allow` (auto-approve, skip classifier) —
   existing + new.
5. `softDeny` (classifier blocks unless an `allow` exception matched) — new.
6. **Classifier** (block/pass on the remaining calls) — new.
7. Default policy (`defaultPolicy`) — existing, for when auto mode is
   *off*.

When auto mode is **off** (no `--auto`, no `autoMode` block), steps
2/4-allow/5/6 are skipped and behavior is identical to today.

### CLI surface

| Flag | Effect |
|------|--------|
| `--auto` | Enable auto mode (classifier on). Implies the gate is active; does *not* imply `--prompts` (auto mode *replaces* prompting for the auto-approvable set). |
| `--auto-env <json>` | Inline `autoMode.environment` override for this run (automation/SDK). |
| `--auto-allow <csv>` | Append to `autoMode.allow` for this run (lift-only, additive over settings). |
| `--auto-deny <csv>` | Append to `autoMode.hardDeny` for this run. |

`--auto` + `--prompts` is legal: `ask` rules still prompt, everything
else goes through the classifier. `--auto` + `--yes` is legal but
redundant (`--yes` already turns every `ask` into `auto_allow`; the
classifier still blocks hard-deny/exfiltration calls that `--yes`
alone would have let through — this is the *whole point* of auto mode
vs. blanket `--yes`).

### Where the code lives

| Concern | File | Change |
|---------|------|--------|

| Settings struct + parser | `src/coding/config/settings.zig` | Add `auto_mode_*` fields + `applyAutoModeSection` (user-layer only) |
| CLI flags | `src/coding/config/cli.zig` | `--auto`, `--auto-env`, `--auto-allow`, `--auto-deny` |
| Wire classifier into the gate | `src/coding/security/permissions.zig` | `Store` gains `auto_env: ?*const AutoEnv` + `auto_allow` / `auto_soft_deny` / `auto_hard_deny` sets; `Store.check` calls `auto_mode.classify` when `auto_enabled` and no prior rule matched |
| Config resolver | `src/coding/config.zig` | Load `autoMode` from user settings only; build `AutoEnv`; seed the store |
| Denial messages | `permissions.zig` (`beforeToolCall`) | Include the classifier's `rule_name` + `reason` in the synthesized tool error |
| `/permissions` slash | `coding/slash.zig` | Show auto-mode status + effective env summary |
| Docs / spec | `docs/spec/v2.md` (§4.x), this doc | New section; mark decided |

The classifier is a **pure** module with no I/O — it takes the already
extracted command/args and the `AutoEnv` and returns a verdict. This
keeps it unit-testable in isolation (same pattern as `path_safety.zig`
and `env_denylist.zig`).

### Bash command understanding

`fingerprintBash` today gives only the verb (`git`). The classifier
needs more: the *full command string* for pattern matching against
`allow`/`deny` globs (e.g. `Bash(git push *)`) and for detecting
destinations (the URL in a `curl`, the remote in a `git push`).

We already extract the raw `command` via `extractBashCommand`. The
classifier will receive the full command string and apply:

- **Glob matching** against `Bash(<pattern>)` entries (Claude Code
  uses `Bash(git push *)` syntax). A small glob matcher (trailing `*`
  + literal prefix) covers the documented patterns; full globbing is
  over-engineering for v1.
- **Destination extraction** for known verbs: `curl`/`wget` → URL arg;
  `git push` → remote name → resolve against `git_remotes`; `git push`
  to a URL → check trust list. This is heuristic and intentionally
  conservative — when in doubt, block.

### Trusted-by-default

Matching Claude Code: by default the classifier trusts

- the **working directory** (writes/edits inside `workspace_root` pass),
- the **current repo's configured git remotes** (`git config --get
  remote.*.url`, parsed once at session init and cached on `AutoEnv`).

Everything else is "external" until added to `autoMode.environment`.

## Implementation plan (phased)

### Phase 1 — Classifier core + destructive rules (no settings yet)
- New `security/auto_mode.zig`: `AutoEnv` (empty), `classify()`, the
  destructive/irreversible rule family, glob matcher.
- Unit tests: `rm -rf /` blocks; `git push --force origin main` blocks;
  `go test ./...` passes; `zig build` passes.
- No wiring yet — pure library.

### Phase 2 — Wire into `Store.check`
- `Store` gains `auto_enabled: bool`, `auto_env: ?*const AutoEnv`,
  `auto_hard_deny` / `auto_soft_deny` / `auto_allow` sets.
- `Store.check`: when `auto_enabled` and the static overlay didn't
  decide, call `classify()`; map `block*` → `auto_deny` with the rule
  name in a new `Decision`-adjacent field (or extend `Decision` to
  carry a reason — see open question).
- `beforeToolCall` surfaces the classifier reason in the tool error.

### Phase 3 — Settings + CLI
- `settings.zig`: parse `autoMode` from **user layer only**.
- `cli.zig`: `--auto` and friends.
- `config.zig`: resolve `AutoEnv`, seed store sets, parse git remotes
  at session init.
- Integration: `--auto` on a sample repo, verify destructive blocks
  fire and routine commands pass.

### Phase 4 — Exfiltration + SCM-target rules
- Destination extraction for `curl`/`wget`/`git push`/`scp`/`rsync`.
- `AutoEnv.trusted_domains` / `trusted_repos` consulted.
- Web tools (`web_fetch`, `web_search`): block fetches to non-trusted
  domains when in auto mode? (Claude Code's classifier focuses on bash
  + write; web tools are a Franky-specific extension — decide in this
  phase.)

### Phase 5 — Polish
- `/permissions` shows auto-mode state.
- Denial messages include the matched rule name in `[Brackets]` like
  Claude Code so users know what to `allow` next.
- Spec entry in `v2.md`; move this doc to `decided/`.
- Optional follow-up: `/auto-mode-setup` slash command that drafts
  environment entries from recent denials.

## Open questions

1. **Carrying the rule name on `Decision`.** Today `Decision` is a
   bare enum and the denial reason is a fixed string in `beforeToolCall`.
   Cleanest: extend `Store.check` to return a small struct
   `{ decision: Decision, rule_name: ?[]const u8, reason: ?[]const u8 }`
   rather than mutating `Decision`. This is a small refactor of the
   ~6 call sites. Alternative: a thread-local / out-param. Prefer the
   struct — it's the kind of change that's cheap now and painful later.

2. **Should `web_fetch` / `web_search` go through the classifier?**
   Claude Code's auto mode is bash/write-focused. Franky exposes web
   tools to the model directly. Proposal: in auto mode, `web_fetch`
   to a non-trusted domain → `block` with `[Data Exfiltration]` (a
   fetch can leak via the URL), but `web_search` → `pass` (search
   queries are low-risk and the provider is already trusted). Open for
   discussion.

3. **LLM-backed classifier as a later option.** Keep the
   `classify()` signature stable so a future implementation can swap
   the rule engine for a provider call (with a timeout + fall-back to
   the local rules on failure). Not built now.

4. **`autoMode` in project settings — enforce the ignore.** The
   settings loader currently merges project + user. We need an
   explicit skip for the `autoMode` key when reading the project
   layer. Simple: in `applyAutoModeSection`, only call it from the
   user-layer pass.

## Risks

- **False positives** blocking legitimate work → frustration.
  Mitigation: `allow` exceptions + clear denial messages naming the
  rule. Ship Phase 1 (destructive only) first — it has the lowest
  false-positive rate.
- **False negatives** letting something dangerous through → the whole
  point. Mitigation: conservative defaults, `hardDeny` for known-bad
  patterns, and the existing `path_safety` / `env_denylist` layers
  remain in place underneath.
- **Heuristic command parsing** can be fooled (`git -c x=y push`,
  nested quotes). This is the same limitation Claude Code documents
  for its `Bash(git push *)` rules. We'll document it and recommend
  `permissions.deny` + a PreToolUse-style hook for hard guarantees
  (Franky doesn't have hooks yet — out of scope).
