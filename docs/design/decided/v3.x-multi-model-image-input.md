# Multi-Model Image Input (v3.x)

**Status:** implemented · **Scope:** LLM image *input* (vision) across all providers · **Not in scope:** image *output/generation* (DALL·E, gpt-image, etc.)

---

## 1. Current state (analysis)

### 1.1 Type layer — `src/ai/types.zig` ✅ ready
- `ImageContent { data: []const u8, mime_type: []const u8 }` already exists (base64, no `data:` prefix).
- `ContentBlock` is a tagged union with an `.image` variant; `dupe`/`deinit` handle it.
- `Message.content: []ContentBlock` — a user message may already carry text **+** image blocks.
- `Capabilities { vision: bool, … }` exists; the model catalog populates it (Ollama `show` flags, hardcoded for known OpenAI models, `docs/spec`).

### 1.2 Provider request serialization (the "input" direction)

| Provider file | api tag | Image input serialized? | Shape emitted |
|---|---|---|---|
| `anthropic.zig` | `anthropic` | ✅ yes (user **and** tool_result) | `{"type":"image","source":{"type":"base64","media_type":…,"data":…}}` |
| `openai_chat.zig` | `openai-chat-completions` | ✅ yes (user content parts) | `{"type":"image_url","image_url":{"url":"data:<mime>;base64,<data>"}}` |
| `google_gemini.zig` | `google-gemini` | ✅ yes | `{"inlineData":{"mimeType":…,"data":…}}` |
| `openai_gateway.zig` | `openai-compatible-gateway` | ✅ yes (delegates to `openai_chat`) | — |
| `google_vertex.zig` | `google-vertex` | ✅ yes (delegates to `gemini`) | — |
| `openai_responses.zig` | `openai-responses` | ❌ **drops images** — `else => "[unsupported]"` (line 128) | should emit `{"type":"input_image","image_url":"data:<mime>;base64,<data>"}` |
| `faux.zig` | `faux` | ⚠️ ignores (test provider; fine, but no assertion image was received) | — |

**Net:** 4 of 5 distinct wire formats already send images. Only `openai-responses` is broken (silently replaces images with `[unsupported]` text).

### 1.3 Input paths — how images enter the transcript ❌ **none exist**
Every entry point constructs user messages as **text-only**:

| Entry point | File:line | Current behavior |
|---|---|---|
| CLI `--prompt` / positional | `coding/modes/print.zig:322` | `content[0] = .{ .text = … }` |
| Proxy `/review` rebuild | `coding/modes/proxy.zig:1597, 2214` | text only |
| RPC `reply` method | `coding/modes/rpc.zig:692` | `extractPromptText` → text only; no image params parsed |
| CLI flags | `coding/config/cli.zig` | no `--image`/`--file`/`--attach` flag; `prompt: []const u8` only |
| SDK | `sdk.zig` | no image helper; callers *could* hand-build `ContentBlock{ .image = … }` but it's undocumented and there's no loader |

**This is the core gap.** The plumbing to the providers exists, but there is no way for a user, RPC client, or SDK caller to actually attach an image.

### 1.4 Other touch points
- **Persistence** (`coding/session/persistence.zig:462, 649`): ✅ round-trips `.image` (serializes `data`+`mimeType`, deserializes back). Resume across sessions works.
- **Compaction** (`coding/session/compaction.zig:255`): accounts for image bytes (`data.len/8` rough token estimate). OK.
- **Wire encode** (`agent/wire.zig`): only encodes *outbound* agent events; `contentBlocks` count emitted but no inbound image decode.
- **Proxy/UI render** (`coding/modes/proxy.zig:1557, 2634`): `.image => {}` — images are silently skipped in terminal/proxy rendering. No artifact viewer.
- **Capabilities `vision` flag**: populated but **never gated** — nothing checks `model.capabilities.vision` before sending/allowing images. Purely informational (shown in `models` listing).
- **`multimodel-review` skill** (`coding/skills/multimodel-review.md`): runs a text prompt across N models; no image handling.

---

## 2. Gap summary

1. **No input path.** No CLI flag, no RPC param, no SDK helper to attach images.
2. **`openai-responses` drops images** silently (`[unsupported]`).
3. **`vision` capability unused.** No pre-flight check; a non-vision model receives image blocks it can't handle (wastes a request, or 400s).
4. **No size/limits validation.** A 50 MB image would blow the request body and the transcript (persisted) with no guardrail.
5. **No test coverage** for image input end-to-end (faux has no image assertion; no provider test sends an image block).

## 3. Plan (ordered, minimal-diff)

### Phase 1 — Close the provider gap (input serialization)

**1a. `openai_responses.zig` — emit `input_image` parts.**
In the `switch (cb)` at line 122, add an `.image` arm:
```zig
.image => |img| {
    try buf.appendSlice(allocator, "{\"type\":\"input_image\",\"image_url\":\"data:");
    try utils.appendJsonRaw(buf, allocator, img.mime_type);
    try buf.appendSlice(allocator, ";base64,");
    try utils.appendJsonRaw(buf, allocator, img.data);
    try buf.appendSlice(allocator, "\"}");
},
```
(OpenAI Responses API accepts `input_image` with a `data:` URI — same inline-base64 convention as Chat Completions.) Replace the `else => "[unsupported]"` with an `.image`-aware fallback so tool-result images aren't lost either (Responses API: pass image as `output_text`? — actually Responses tool output is text-only; for tool results, keep current text-concat and drop image with a log line).

**1b. `faux.zig` — record received image blocks** (test observability).
In the faux stream fn, when echoing the user message, count `.image` blocks and surface them in the canned reply (e.g. `"received 1 image (image/png, 1234 bytes)"`) so tests can assert the image was accepted.

**Tests:** add unit tests in `openai_responses.zig` and `faux.zig` that build a `Message` with one `.text` + one `.image` block and assert the serialized body contains the expected image JSON / the faux reply mentions the image.

### Phase 2 — Input paths (the actual feature)

**2a. CLI flag `--image <path>` (repeatable) + `--image-stdin`** in `coding/config/cli.zig`:
- New field `images: []const []const u8 = &.{}`.
- For each path: read file, base64-encode, sniff mime from extension (`.png`/`.jpg`/`.jpeg`/`.gif`/`.webp`), build an `ImageContent`, append a `.image` block to the user message *after* the text block.
- `--image-stdin`: read binary image from stdin (mime via `--image-stdin-mime` or default `image/png`).
- Enforce a max size (default 20 MB, configurable) — reject with a clear error before encoding.

**2b. `print.zig` user-message construction (line 322):** when `cfg.images.len > 0`, allocate `content` of length `1 + images.len`, set `[0] = .text`, fill the rest with `.image` blocks. Add a `deinit` path (images are owned by the transcript after append).

**2c. RPC `reply` method** (`coding/modes/rpc.zig`): extend `extractPromptText` → `extractPromptContent` that also parses an optional `images: [{ "path": … } | { "base64": …, "mimeType": … }]` array from `params_raw`. Build multi-block content. Keep backward compat: text-only requests still work.

**2d. SDK helper** (`sdk.zig`): add
```zig
pub fn imageBlock(allocator, path: []const u8) !ContentBlock
pub fn imageBlockFromBytes(allocator, data: []const u8, mime: []const u8) !ContentBlock
```
(does the base64 encode + mime sniff + dupe into owned memory). Document in the SDK header docstring.

### Phase 3 — Capability gating + guardrails

**3a. Pre-flight vision check.** In the agent loop (or at the mode driver before `reg.stream`), if any user/tool-result message in the `Context` contains an `.image` block **and** `model.capabilities.vision == false`, emit a structured error event (`ai.errors.Code` = a new `image_unsupported` or reuse `unsupported_feature`) rather than sending a request that will 400. Surface the model name + a hint to switch to a vision-capable profile. Make this overridable via a `--force-image` flag for gateways that misreport capabilities.

**3b. Size/limits.** Centralize in a helper `ai.utils.validateImage(data_len, mime)` — reject > max bytes, reject unknown mime. Call from CLI loader, RPC parser, and SDK helper. Default max from `coding/config/settings.zig` (new `max_image_bytes`).

### Phase 4 — Observability + rendering

**4a. Proxy/terminal rendering** (`proxy.zig:1557, 2634`): instead of `.image => {}`, emit a placeholder line `[image: <mime>, <N> bytes]` so the user sees something was attached. (Full rendering is out of scope — no image viewer in terminal.)

**4b. Logging** (`agent/loop.zig:2182`): the `.image` trace log currently only prints the block index; add mime + byte count.

### Phase 5 — Tests + docs

- **Unit:** image-block serialization in all 5 provider wire formats (anthropic, openai_chat, openai_responses, gemini, faux).
- **Integration:** CLI `--image` → faux provider asserts image received; round-trip through persistence (save session with image, resume, re-send).
- **RPC:** `reply` with `images` param → transcript contains `.image` block.
- **Capability gate:** non-vision model + image → structured error, no HTTP call.
- **Docs:** update `AGENTS.md` "Providers" row; add a `docs/design/decided/` short note; add SDK usage example in `sdk.zig` header; update CLI help in `cli.zig` docstring.

## 5. What is explicitly NOT done
- Image **output/generation** (DALL·E, gpt-image, Gemini image-out) — out of scope per task.
- Image rendering in the terminal/proxy UI (placeholder only).
- Streaming image upload / URL-only image references (we do inline base64 only, matching existing `ImageContent.data` semantics).
- Changing `ImageContent` shape (it's already correct and persisted).

## 6. Risk / compatibility
- All changes are additive to the wire format and CLI; existing text-only flows are untouched.
- Persistence format for `.image` is unchanged → old sessions with images (if any) still resume.
- The `vision` gate is the only behavioral change that could surprise: a model that previously received (and rejected) images will now be blocked client-side. Mitigated by `--force-image`.
